# PA Investing Workflow

This repository contains a personal-account investing workflow that is being built in phases.

The long-term architecture is:

- Notion as the first user-facing command center.
- Python backend as the compute and workflow layer.
- PostgreSQL as the structured source of truth.
- linked analytics pages for deeper drilldown when Notion is not enough.

The system is intentionally analysis-only. It does not place trades or submit broker orders.

## Current Status

The project has completed the full Phase 1 backend foundation and has started Phase 2, which is now focused on the first visible MVP:

- real Notion integration;
- one live market price API;
- one end-to-end refresh-and-sync workflow;
- a simple trigger surface to run the workflow.

The first MVP target is:

> see fictitious portfolio positions flow from backend truth into a real Notion workspace, with prices, metrics, and signals generated by the backend.

## What Has Been Implemented

### Phase 1: Backend Foundation

Phase 1 is complete.

Implemented:

- Python backend scaffold with FastAPI, SQLAlchemy, Alembic, pytest, Ruff, and Docker files.
- Domain models for instruments, accounts, positions, price points, portfolio snapshots, and signals.
- Database schema and repositories for accounts, positions, prices, signals, portfolio snapshots, and audit events.
- CSV position import for manual portfolio loading.
- Manual price provider for seeded or local price data.
- Portfolio analytics for NAV, unrealized PnL, gross exposure, and net exposure.
- Deterministic rule-based sizing and stop/reference signal generation.
- Fake Notion client and payload mapping for signal sync.
- Mockable LLM summarization interface.
- Daily review workflow and persistence for snapshots, signals, and audit events.
- Minimal analytics pages and API routes:
  - `GET /health`
  - `GET /analysis/portfolio`
  - `GET /analysis/signal/{signal_id}`
- Docker Compose scaffold for backend plus PostgreSQL.

What Phase 1 gives us today:

- we can load positions manually;
- compute portfolio state and signals;
- persist the results in PostgreSQL;
- exercise the workflow in tests;
- generate Notion-shaped payloads.

What Phase 1 does not yet give us:

- real Notion API sync;
- real live market prices;
- a single end-to-end “refresh portfolio and push to Notion” workflow;
- live broker integrations.

### Phase 2: MVP Integration Work

Phase 2 is in progress.

Completed so far:

- live integration settings were added to config:
  - `PA_MARKET_DATA_PROVIDER`
  - `PA_ALPHA_VANTAGE_API_KEY`
  - `PA_NOTION_SIGNALS_DATABASE_ID`
  - `PA_NOTION_DAILY_REVIEW_DATABASE_ID`
- cached dependency wiring was added for runtime settings access.
- live Notion client support was added behind the existing `NotionClient` interface.
- live Notion upsert behavior was implemented with:
  - lookup by `External ID`
  - create on miss
  - update on match
  - body-content convergence for the current single-paragraph page model
- Notion sync was expanded to support:
  - `Signals`
  - `Daily Review`
- Alpha Vantage price provider was implemented and hardened through review-driven fixes.
- the refresh-and-sync workflow was implemented:
  - load open positions;
  - fetch current prices;
  - persist price points;
  - update position marks;
  - compute and persist snapshot and signals;
  - sync `Signals` and `Daily Review` into Notion
- a first API trigger surface was added:
  - `POST /workflows/refresh-and-sync`
- backend runbook documentation was expanded for:
  - live Notion configuration
  - Alpha Vantage configuration
  - migrations
  - API triggering
  - safe local runs with Notion disabled

## What Still Needs To Be Done For The First MVP

To reach the first MVP where you can see fictitious positions in a real Notion workspace, the remaining work is:

1. Prepare a demo dataset of fictitious positions.
   For the first MVP, this can be simple seeded positions such as:
   - `AAPL`
   - `SPY`
   - `BTC-USD`

2. Configure a real Notion workspace for the demo.
   At minimum, the backend needs working database IDs for:
   - `Signals`
   - `Daily Review`

3. Run the workflow end to end against the fictitious data.
   The successful MVP outcome is:
   - positions exist in the backend database;
   - live or simulated current prices refresh;
   - portfolio snapshot and signals are generated;
   - Notion shows the synced results without manual page editing.

4. Optionally add a tiny seed/import helper for repeatable demos.
   This is not strictly required, but it would make the MVP much easier to rerun.

## Definition Of The First MVP

The first MVP is **not** a full investing platform.

It is successful when we can demonstrate:

- a PostgreSQL-backed portfolio with fictitious positions;
- one live or live-like price refresh path;
- backend-generated metrics and signals;
- successful sync into a real Notion workspace;
- one simple manual or API trigger to run the loop on demand.

It does not yet require:

- broker read-only connectors;
- agent explanations;
- Obsidian integration;
- a custom frontend;
- notifications;
- richer charting beyond the existing placeholder analysis pages.

## Recommended Next Build Order

To get the first MVP in front of you as quickly as possible, the next order should be:

1. seed fictitious positions in the database;
2. connect the backend to your real Notion databases;
3. run the demo loop and verify the Notion output visually;
4. add a repeatable seed/import helper if the manual setup feels too fiddly.

## Important Boundaries

The project keeps these boundaries on purpose:

- Notion is a UI adapter, not the source of truth.
- PostgreSQL remains the structured source of truth.
- secrets stay in backend config, never in Notion.
- deterministic backend rules own numeric recommendations.
- the system remains read-only and analysis-only.
